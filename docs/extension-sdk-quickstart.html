BuildSuite extension SDK

From zero to a customised BuildSuite in four steps

An extension is an ordinary Frappe app with one extra line and a small JavaScript file. It adds pages, tiles and sections to BuildSuite Core without rebuilding Core, and uninstalling it removes them again.

Built works on the feat/extension-sdk branch today Planned designed, not built yet
Step 1

Scaffold the app

Built: scaffold command
Terminal
# from your bench
bench new-buildsuite-extension acme_ext --title "Acme Extension"
bench get-app ./acme_ext
bench --site mysite install-app acme_ext

About 30 seconds. A complete working demo lives in examples/buildsuite_demo_extension.

What you get
acme_ext/
├── pyproject.toml
└── acme_ext/
    ├── hooks.py              # declares your extension
    ├── modules.txt
    └── public/js/

Step 2

Declare it and customise

Built: hook, page, slot, tile, view override, form hooks, settings pagePlanned: resource registry
hooks.py (the only BuildSuite line)
buildsuite_frontend_extensions = [{
  "name": "acme_ext",
  "js":   "/assets/acme_ext/js/extension.js",
  "min_sdk": "1.0",
}]

# a settings page with no JavaScript: a Single DocType
buildsuite_settings_pages = [{
  "doctype": "Acme Settings",
  "group": "Acme", "label": "Acme settings",
}]

Frappe lists the hooks of installed apps only, so the extension is active exactly where the app is installed. The Custom Fields it adds are ordinary Frappe fixtures.

public/js/extension.js
export default function register(sdk) {
  // a new page inside the app shell
  sdk.routes.add({ path: "site-diary", component: SiteDiary });

  // a tile on the Sales workspace
  sdk.workspaces.addTile("sales", {
    label: "Site diary", to: "/site-diary",
  });

  // a component above or below ANY page, bespoke or not
  sdk.slots.add("page.app-home.top", Banner);

  // a control for a Custom Field on a bespoke form (Quotation today)
  sdk.doctype("Quotation").on({ fields: ["region"] });
  sdk.slots.add("form.Quotation.top", RegionControl);

  // replace a Core page, or render around it
  sdk.views.override("settings-app-icon-diagnostics", MyDiagnostics);
  sdk.views.wrap("settings-data", MyFrame);

  // hooks on the generic DocType form ("*" = every doctype)
  sdk.doctype("*").on({ beforeSave(payload) { /* throw to refuse */ } });

  // planned: columns and sections on an existing resource
  sdk.resources("Project").list.addColumn({ field: "custom_region" });
}
Step 3

Load it

Built: loading at runtime, no build step
Terminal
# extension.js is plain JavaScript: Vue arrives as sdk.vue
bench --site mysite migrate   # only if you ship fixtures or doctypes

Reload the app. Core loads extension.js at runtime from the installed app, checks the SDK version, and calls register(sdk). An extension that fails to load or throws while rendering is logged and skipped, and the page around it keeps working.

Core's own bundle is never rebuilt, and Core's build never depends on which apps are on the bench.

Planned: phase 4

An onboarding page asks "What do you want to change?", or lets someone drag a section into a form. It stores the same declarations as data on the site, and Core applies them exactly as it applies an extension's. Precedence is Core, then installed apps, then the site's own customisations.

Where the SDK lives

buildsuite-sdk-py

Frappe helpers: seed if missing, permissions, reports, workflows, test helpers. Depends on Frappe only.

@buildsuite/sdk

Controls, composables, registries and types. Core consumes it the same way an extension does.

buildsuite-extension-template

The starter app that new-buildsuite-extension writes today from a template inside Core; a separate repo comes later.

The two SDKs version independently with a published compatibility matrix. The split happens once the controls are extracted from Core and the public surface has settled.
